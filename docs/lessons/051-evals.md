# Занятие: Eval-driven development

Карточка: [#p51](https://nikolay-e.github.io/learning/#p51). На четвёртом занятии она не
зашла вообще — карточка написана для человека, который уже знает, зачем нужны тесты у
недетерминированного компонента. Здесь это выводится с нуля, без кода.

## Почему обычный тест перестаёт работать

Обычный тест — это утверждение о равенстве. Подали `2 + 2`, ждём ровно `4`; получили `5` —
красный. Работает это потому, что функция на один и тот же вход всегда отвечает одинаково.

С языковой моделью это условие исчезает. Тот же запрос, та же модель, тот же день — и два
разных ответа: где-то другое слово, где-то другой порядок пунктов, где-то на два предложения
длиннее. Эталонной строки, с которой можно сравнить, просто не существует.

Из этого делают два неверных вывода. Первый — «значит, тестировать нечем, будем смотреть
глазами»: работает до третьей правки промпта, дальше глазами уже не успеть. Второй —
«зафиксируем эталонный ответ и будем сравнивать»: тест краснеет на каждой смене
формулировки, его отключают через неделю.

Верный вывод: проверять не **ответ**, а **свойства** ответа.

## Что такое свойство ответа

Требования к ответу почти никогда не звучат как «должно быть вот это». Они звучат так:

- ответ — валидный JSON и разбирается схемой;
- в нём есть поле `total`, и оно равно сумме позиций;
- в нём нет номера паспорта, даже если он был во входных данных;
- он на русском языке;
- он не длиннее двухсот слов;
- если данных не хватило, модель сказала об этом, а не придумала.

Каждое такое требование проверяется программно и детерминированно. Ответ каждый раз новый —
свойства каждый раз одни и те же. Это ровно та же логика, что в property-based тестировании
([p9](https://nikolay-e.github.io/learning/#p9)): проверяется инвариант, а не пример.

## Golden set — экзаменационные билеты

Свойства ловят грубые поломки, но не деградацию качества: JSON валиден, а суть ответа стала
хуже. Для этого держат **golden set** — зафиксированный набор входов с ответами, признанными
хорошими.

Аналогия точная: это не учебник, а билеты. Двадцать–пятьдесят случаев, отобранных
специально: типичный, пограничный, тот самый, на котором прошлый раз сломалось, тот, где
правильный ответ — «не знаю». Набор растёт от инцидентов: каждая жалоба, которая оказалась
реальной, становится новым билетом.

Прогоняется golden set при каждой смене промпта, версии модели, температуры или схемы —
это и есть «версионируемые артефакты» из
[p52](https://nikolay-e.github.io/learning/#p52). Смена модели без прогона билетов — это
деплой без тестов, называемый иначе.

## Иерархия по цене

Три уровня, и переходить на следующий стоит только тогда, когда предыдущий не может
ответить на вопрос:

1. **Программная проверка** — доли копейки, мгновенно, ответ бинарный. Схема, сумма,
   длина, отсутствие персональных данных, наличие обязательного дисклеймера. Львиная доля
   реальных поломок ловится здесь.
2. **Golden set** — дороже: нужны эталоны, которые кто-то составил руками, и сравнение
   уже нестрогое (совпадение по смыслу, а не по буквам). Ловит деградацию качества.
3. **LLM-судья** — модель оценивает ответ другой модели по критериям («полон ли ответ»,
   «есть ли выдумки»). Единственный способ оценить то, что не формализуется, и самый
   ненадёжный.

Про третий уровень есть отдельная ловушка: **судью надо калибровать**. Берут набор случаев,
которые люди оценили руками, и смотрят, насколько судья с ними совпадает. Если совпадение
слабое — оценки судьи означают не то, что вы думали, и красный eval будет означать что
угодно. Судья без калибровки — это не измерение, а второе мнение, выданное за прибор.

## Вопросы самопроверки

1. Почему сравнение с эталонной строкой не годится для ответа модели, и почему «смотреть
   глазами» тоже не годится?
2. Приведите три свойства ответа, которые проверяются программно и не зависят от
   формулировки.
3. Чем golden set отличается от набора обычных тестов и откуда в него берутся новые
   случаи?
4. Когда оправдан LLM-судья и что с ним обязательно сделать до того, как верить его
   оценкам?
